# План внедрения и TDD-процесс

Документ дополняет `docs/SDD.md`: как и в каком порядке строим пульт, и как выглядит
«сделано» с точки зрения тестов. Спека — источник истины по требованиям; здесь — процесс.

## 1. TDD-процесс (обязателен для всего кода)

Цикл красный → зелёный → рефактор:

1. Пишем падающий pytest-тест на желаемое поведение (или на баг — тест воспроизводит баг).
2. Запускаем, убеждаемся, что падает **по правильной причине**.
3. Пишем минимальный код, пока тест не пройдёт.
4. Рефакторим, тесты остаются зелёными.

Правила:

- Ни строки рабочего кода без теста. Исключение — тривиальный конфиг/шаблон (и то проверяется smoke-тестом).
- Тест проверяет поведение, а не реализацию. Для таймеров — `freezegun`; для внешних сервисов — подмена адаптера, не «мок ради мока».
- Все фикстуры-файлы (nmap XML, выгрузки, письма) — вымышленные.
- Покрытие: общий порог **80 %** (`pytest --cov-fail-under=80`); модуль формулы КЗИ, генератор RRULE,
  расчёт дедлайнов и drift-дифф — цель 100 % на ветки.

### Определение готовности (DoD) для любой задачи

- [ ] есть тесты (написаны первыми);
- [ ] `make verify` зелёный (ruff + pytest + `manage.py check --deploy`);
- [ ] спека актуальна (если поведение изменилось — правка SDD в том же PR);
- [ ] никаких секретов и реальных персональных данных в коде/тестах/фикстурах;
- [ ] для новых зависимостей — строка-обоснование в PR.

## 2. Тестовый инструментарий

| Инструмент | Назначение |
|---|---|
| `pytest` + `pytest-django` | каркас тестов, `settings`-профиль `test` |
| `factory_boy` | фабрики данных (assets, systems, assessments…), без JSON-простыней вручную |
| `freezegun` | таймеры: напоминания 30/7/1, эскалации, стадии инцидентов, next_due |
| `pytest-cov` | покрытие, порог в CI |
| `responses` / `respx` | HTTP адаптеры (Telegram, messenger webhook, SMTP через locmem) |
| `ruff` | линт + формат (замена black/isort) |
| Django test client | API и шаблонные smoke-тесты |
| Playwright (позже, неделя 11–12) | 3–4 e2e-сценария: login → матрица → test_run с evidence; КЗИ-оценка; обязательство; инцидент |

Слои тестов: **unit** (формулы, RRULE, дедлайны, парсеры) → **integration** (DRF-эндпоинты, права ролей,
загрузка evidence; S3-хранилище подменяется `FileSystemStorage` в тестах) → **smoke UI** (страницы ролей рендерятся)
→ **e2e** (пилотные потоки). Не дублировать слои: поведение, проверенное unit-тестом, в integration повторять
только на уровне доступа/связки.

Целевой каркас (создаётся на неделе 1):

```toml
# pyproject.toml (эскиз)
[tool.pytest.ini_options]
DJANGO_SETTINGS_MODULE = "config.settings.test"
addopts = "-q --cov=apps --cov=collector --cov-fail-under=80"

[tool.ruff]
line-length = 100
```

## 3. Спринты (по 1 неделе)

Критерии «готово» — из черновика заказчика, уточнены под выбранный стек (Django-монолит,
отдельного `app-ui` нет; collector — отдельный сервис профиля `scan`).

### Неделя 1 — Инфраструктура и каркас
**Задачи:** репозиторий (pyproject, ruff, pytest, Makefile), Docker Compose (nginx/web/worker/beat/
postgres/redis/s3), TLS, `.env.example`, RBAC (5 ролей из SDD §4), базовый `audit_log`,
бэкап-скрипты `ops/`, `manage.py check --deploy` в `make verify`.
**Tests-first:** settings-профиль test; audit-мидлварь пишет событие; роли разграничивают доступ к тестовой странице; smoke: страница логина рендерится.
**Готово, если:** UI открывается по HTTPS; вход под 4+ ролями даёт разные разделы; бэкап по расписанию создан и restore проверен на тестовую БД.

### Неделя 2 — Network scopes + коллектор
**Задачи:** CRUD `segments` (+окно скана); collector: Mikrotik SNMP/API, ICMP sweep, nmap `top100` (XML-парсер), upsert assets, `asset_events`, `scan_runs`; запрет сканов вне окна/scope.
**Tests-first:** парсер nmap XML (фикстуры до/после), upsert и дедупликация (MAC-first; переиспользование IP → новый актив), правило «пропажа после 3 промахов», отказ скана вне окна, бюджет скана.
**Готово, если:** в `assets` появляются узлы с `last_seen`; отчёт «новые активы за сутки»; распределение по площадкам/сегментам.

### Неделя 3 — Реестр ИС и карта ответственности
**Задачи:** CRUD `systems`, `persons`, `system_components`; экран «Unknown assets»; владельцы
(ЛИС, PACS, Аптека, сайт, МИС, ЗУП, ВКС, телемедицина=UNKNOWN, инфраструктура).
**Tests-first:** запрет сохранения ИС без владельца и authority; фильтр «unknown»; привязка активов.
**Готово, если:** по каждой ИС есть owner + authority (FULL/SHARED/EXTERNAL/UNKNOWN); ключевые активы привязаны.

### Неделя 4 — Каталог требований и контролей
**Задачи:** `norm_acts/requirements/controls/requirement_control_map`; data-миграция «верхнеуровневый каталог
117/КИИ/ПДн/СКЗИ» + топ-15 контролей и тестов; матрица «ИС → контроль» с применимостью.
**Tests-first:** data-миграция идемпотентна; матрица считает «применимо, но не внедрено/не подтверждено»; статусные переходы контроля.
**Готово, если:** видна матрица ИС×контроли; список «применимо, но не внедрено/не подтверждено».

### Неделя 5 — Evidence
**Задачи:** S3-хранилище (SeaweedFS) + `evidence_objects` (sha256, valid_until, конфиденциальность), загрузка/скачивание через web,
`evidence_links`, процесс «скан письма» (`letter` + метаданные), отчёт «evidence истекает через N дней».
**Tests-first:** sha256 совпадает; whitelist типов и лимит размера отклоняют плохой файл; привязка/отвязка линков; письмо «вх/исх» видно в журнале переписки; скачивание запрещено роли без прав.
**Готово, если:** скан письма в ФСТЭК загружен и привязан к объекту КИИ/обязательству; отчёт об истечении работает.

### Неделя 6 — Обязательства + уведомления
**Задачи:** `obligation_templates` (RRULE + lead_days + эскалации; стартовый набор — SDD §3.5), материализация инстансов на 12–18 мес,
календарный экран, напоминания 30/7/1, эскалации при просрочке; сервис `notify()` + каналы in-app и SMTP
(адаптеры Telegram/messenger — каркас).
**Tests-first:** генерация инстансов за период (freezegun); напоминание ровно за 30/7/1; эскалация после просрочки по шагам политики; дедупликация уведомлений; retry при ошибке SMTP.
**Готово, если:** календарь обязательств построен на 12 мес; просрочка меняет статус и эскалация уходит адресату.

### Неделя 7 — КЗИ: справочники + ввод
**Задачи:** `kpi_groups/kpi_items` (+веса), создание `assessment` (тип/период/скоуп), экран ввода `kpi_values`,
обязательные evidence для ненулевых значений, блокировка закрытия при NULL.
**Tests-first:** закрытие при NULL в обязательном KPI запрещено; value>0 без evidence запрещено; value=0 разрешён (≠NULL).
**Готово, если:** создана оценка КЗИ и внесены значения по 2–3 ИС (ЛИС/PACS/Аптека); «неполную» оценку закрыть нельзя.

### Неделя 8 — КЗИ: расчёт, снапшоты, «почему не 1»
**Задачи:** формула из SDD §3.4 (`apps/kzi/formula.py`), cap-штрафы окон, снапшот `details`,
экран «почему не 1» (вклад групп, донор минимума, ссылки на evidence).
**Tests-first:** unit на формулу: равные значения, пропуски необязательных, кап штрафа, min-донор, округление; снапшот воспроизводит расчёт 1:1.
**Готово, если:** по кнопке получаем КЗИ + объяснение, какие KPI и какая ИС тянут вниз.

### Неделя 9 — План мероприятий
**Задачи:** `remediation_plans` из «почему не 1», задачи с владельцами и сроками до следующей оценки,
контроль статусов, отчёт руководству (XLSX + печатная HTML).
**Tests-first:** план генерирует задачи по каждому проблемному KPI (сортировка по весу); дедлайны ≤ следующей оценки; выгрузка содержит обязательные колонки.
**Готово, если:** из оценки создаётся план со статусами и дедлайнами; отчёт выгружается.

### Неделя 10 — Инциденты + таймеры
**Задачи:** реестр инцидентов, справочник правил стадий (1ч/T1/T2), таймеры, evidence отправки, закрытие; интеграция с `notify()`.
**Tests-first:** расчёт deadline по правилу (freezegun); просроченная стадия видна как overdue; закрытие стадии требует evidence; закрытие инцидента при открытых стадиях запрещено.
**Готово, если:** инцидент показывает таймеры и просрочки; отправка фиксируется evidence.

### Неделя 11 — Отчётность и дашборды
**Задачи:** дашборды по ролям; выгрузки «состояние контролей», «просрочки», «покрытие evidence»,
«неизвестные активы», «КЗИ отчёт»; 1-страничный отчёт руководству.
**Tests-first:** права на выгрузки по ролям; обязательные колонки и фильтры; «1 страница» рендерится.
**Готово, если:** руководство видит 1-страничный отчёт (риски/просрочки/план); владелец ЛИС видит только ЛИС и свои обязательства.

### Неделя 12 — Пилот и регламенты
**Задачи:** пилот на ЛИС/PACS/1С-Аптека; регламент ведения evidence и периодических проверок;
обучение; e2e Playwright на пилотные потоки.
**Готово, если:** по 3 ИС закрыты базовые контроли с evidence; календарь обязательств работает; RACI понятен.

## 4. Ветки, коммиты, ревью

- `main` — всегда зелёный (`make verify`); задачи — в feature-ветках `feat/…`, `fix/…`.
- Conventional Commits: `feat(kzi): взвешенный расчёт групп`, `fix(obligations): …` (описание можно по-русски).
- Ревью: для кода, трогающего auth/загрузки/права — обязательный прогон агента `security-reviewer`
  (ECC) + `code-reviewer`; для фронтовых шаблонов — smoke-скриншоты.
- Изменение поведения = правка `docs/SDD.md` в том же PR.
