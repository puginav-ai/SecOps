# Регламент: ведение evidence, периодические проверки, инциденты, КЗИ

Рабочий документ пилота (неделя 12). Источник требований — `docs/SDD.md`;
изменения регламента вносим через правку SDD и этого файла.

## 1. Роли и ответственность (RACI)

| Процесс | ИБ-админ | ИБ-офицер | ИТ | Владелец ИС | Руководство |
|---|---|---|---|---|---|
| Реестр ИС и владельцы | A | R | C | R (свои ИС) | I |
| Применимость контролей | A | R | C | C | I |
| Периодические проверки контролей | A | R | R (ИТ-контроли) | C | I |
| Evidence (загрузка, сроки) | A | R | C | C | I |
| Обязательства и сроки | A | R | C | R (свои) | I |
| Инциденты (регистрация, стадии) | R | A | C | C | I (эскалации) |
| КЗИ/ПЗИ: оценка и план | A | R | C | C | I |
| Отчёт руководству | A | R | — | — | I |

R — исполняет, A — отвечает за результат, C — консультирует, I — информируется.

## 2. Evidence: что и как храним

- **Evidence = первичный артефакт**: письмо (вх/исх), акт, договор, выгрузка системы,
  отчёт, скриншот, скан. Словесные заверения — не evidence.
- Загружаем **только через консоль** (`/evidence/upload/`), не «в папке на диске»:
  консоль считает `sha256`, следит за белым списком типов и лимитом размера.
- Указываем: вид, дату документа, **срок действия** (для договоров/аттестатов/поверок) —
  по нему работает отчёт «evidence истекает через 30 дней».
- Привязываем evidence к объекту (контроль/проверка/ИС/инцидент/обязательство)
  через раздел связей — покрытие evidence строится по связям.
- Письма ФСТЭК: отдельный вид «письмо», обязательны направление, номер, дата,
  корреспондент; контроль ответа — обязательством «Контроль ответа ФСТЭК».
- Скачивание: разрешено ИБ/ИТ/владельцам ИС; роль «Руководство» видит метаданные.

## 3. Периодические проверки (цикл)

1. Контроль имеет проверки с периодичностью (`frequency_days`) и критерием прохождения.
2. ИБ-офицер прогоняет проверку в карточке матрицы («тест»): результат + evidence,
   дата следующей проверки считается автоматически.
3. **«Подтверждено» ставится только после прогона**: без проверки система не даст.
4. Пробелы («запланировано/внедрено/не соответствует») — на дашборде и в отчёте
   руководству; применимо, но не внедрено — разбирается ежемесячно.
5. Исключение (`ExceptionApproved`) — только ИБ-админ, обязательно с evidence решения
   руководства и сроком пересмотра.

## 4. Инциденты

- Регистрация — не позднее **1 часа** с обнаружения (для КИИ — срочное уведомление
  руководства по правилу «1 час»).
- Стадии (T1/T2, регулятор, ПДн) разворачиваются автоматически; каждая стадия
  закрывается **только с evidence отправки** (письмо/скрин/квитанция).
- Просроченные стадии — на дашборде и на следующий рабочий день в эскалации ИБ-админу.
- Инцидент закрывается после разбора, когда все стадии отправлены.

## 5. Обязательства

- Напоминания владельцу — за 30/7/1 день; просрочка эскалируется по политике шаблона.
- Где помечено «закрытие с evidence» (КЗИ, бэкапы, ФСТЭК) — закрывать без evidence нельзя.

## 6. КЗИ/ПЗИ

- КЗИ — раз в 6 месяцев, ПЗИ — раз в 2 года (шаблоны обязательств).
- Закрытие оценки: все обязательные KPI заполнены, значения > 0 — с evidence.
- План мероприятий формируется из «почему не 1»; сроки ≤ следующей оценки.

## 7. Обучение (сценарий 30 минут)

1. (5 мин) Дашборд: цифры, риски, откуда они берутся.
2. (7 мин) Реестр: активы → Unknown assets → привязка к ИС; владельцы.
3. (8 мин) Матрица: фильтр «только пробелы», прогон одной проверки с evidence,
   перевод в «подтверждено».
4. (5 мин) Evidence: загрузка письма, срок действия, привязка.
5. (5 мин) Инцидент: регистрация, таймеры, закрытие стадии с evidence.
6. (5 мин) Отчёт руководству (1 стр.) и выгрузки XLSX.

Контрольный вопрос после обучения: «где лежит доказательство проверки №X и когда
истекает его срок?» — ответ должен находиться в консоли за < 1 минуту.
